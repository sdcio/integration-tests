# 02 — `tests/05-cache-backend` suite (CRUD round-trip + restart-recovery)

**What to build:** A new, dedicated Robot suite at `tests/05-cache-backend/`, scoped to SR Linux only (following the `04-sensitive` precedent — no SR OS coverage), containing two scenarios:

1. **CRUD round-trip**: create an intent, confirm the device applies it, then confirm `GetIntent`/`BlameConfig` read back correctly. This proves reads flow through `ConfigReadService` rather than any local, in-process state.
2. **Restart-recovery**: restart the `data-server-controller` StatefulSet and confirm previously-applied intents are still readable afterward. This proves correctness depends on `TargetSnapshot` via `ConfigReadService`, not an in-process cache that would be lost on restart. Per this repo's reconciler-timing conventions, the post-restart check must poll/retry for readiness, not assert immediately.

Only external, behavioral assertions belong in this suite — Kubernetes resource state, `GetIntent`/`BlameConfig` output, and device-observable config — not internal `cache.Client` call assertions, matching this repo's existing validation-layer convention.

Explicitly deferred (do not attempt here): multi-target `ConfigSet` fan-out under `Cache.Type: config-server`, and interaction with the `04-sensitive` pipeline.

**Blocked by:** 01 (needs the `cache_type`/suite-selection wiring in `single.yml` to actually run this suite against the config-server-backed cluster in CI; without it there's no way to verify the suite is really exercising `ConfigReadService` rather than the default `local` backend).
