# Config-server cache backend gets its own dedicated CI job, not a second full suite run

Context: [data-server#471](https://github.com/sdcio/data-server/pull/471) + [config-server#476](https://github.com/sdcio/config-server/pull/476) add a `Cache.Type: config-server` backend, additive and meant to be behaviorally identical to the existing `local` backend behind the same `cache.Client` interface. `Cache.Type` is a process-wide, deploy-time setting (one value baked into `data-server`'s ConfigMap, read once at startup) — there is no way to exercise both backends against a single running deployment.

Decided:
- Coverage lives in a **new, small, dedicated suite** (`tests/05-cache-backend`, following the `04-sensitive` precedent), not a second full run of `02-crud`/`03-deviations` against the alternate backend. The suite asserts the *seam* (a CRUD round-trip through `ConfigReadService`, plus a `data-server-controller` restart-recovery check proving reads survive a restart) rather than re-proving the full CRUD/deviation matrix a second time.
- This suite runs in a **second, separate CI job** that deploys its own cluster from scratch with `cache.type: config-server` baked in from the start, running only `00-setup` + `01-crs` + `05-cache-backend` (skipping `02`/`03`/`04-sensitive`) — not a mid-job `kubectl rollout restart` of `data-server-controller` against the same cluster used for the `local`-backend suites. The latter would save one cluster bring-up but risks cross-contaminating state between backends (in-flight candidates, config-server's own controller churn) inside one StatefulSet lifecycle.
- Requested by this repo’s dispatch `cicd.yml` and by data-server / config-server PR CI (each a second `single.yml` call). Not requested by Pairs-with. Not added to `matrix-cicd.yml` — the matrix is version-compatibility coverage, orthogonal to the cache backend, and would re-multiply the cost this design avoided.

Rejected: rerunning existing suites against both backends (defeats the goal of not doubling suite runtime); mid-job pod restart instead of a second job (cheaper but couples backend lifecycles); matrix-wide coverage (multiplies cost for orthogonal concern).

Refined (2026-08): suites `04-sensitive` and `05-cache-backend` are no longer auto-discovered — each gets an explicit `single.yml` step gated by `suites_to_run`, because they carry deploy-time constraints (local-only vs config-server-backed) that a glob cannot enforce. Auto-discovery continues from `06+` only. Default `suites_to_run` includes `04-sensitive` so the local-backend job's behavior is unchanged; `05-cache-backend` is listed only by the cache-backend job. Workflow validation rejects `05-cache-backend` unless `cache_type: config-server`; the suite's own Setup fails fast if the deployed ConfigMap does not carry that cache type. Explicit `04`/`05` steps no-op when that suite directory is absent from the checked-out integration-tests revision, so Pairs-with to an older ref does not `robot` a missing folder.

Refined (2026-08, callers): Pairs-with does not run this repo's `cicd.yml` and does not select the reusable workflow YAML — callers pin `single.yml@main` for the local-backed job. Dispatching this repo's `cicd.yml` is not enough for PR coverage. data-server and config-server PR CI must each request a Cache-backend job (second `single.yml` invocation with `cache_type: config-server`).

Refined (2026-08, full matrix on cache-backend): the cache-backend job also runs `02-crud` and `03-deviations` on the config-server-backed deploy (`suites_to_run: 00-setup,01-crs,02-crud,03-deviations,05-cache-backend`). `04-sensitive` remains local-only. Until this `single.yml` guard lives on `main`, cache-backend callers pin `uses: …/single.yml@config-server-cache-backend` so GitHub executes the workflow that allows that combination; Pairs-with still selects the Robot tree (`integration-tests#115`).
